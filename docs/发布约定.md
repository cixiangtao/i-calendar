# 发布约定

## 用户已确定的安排

- 项目名称：i日历；仓库名称：`i-calendar`。
- 项目信息、README、版本说明、发布说明与 commit 描述使用中文。
- 在本地持续开发并逐次提交；达到 1.0 且完成验收后，再提交 GitHub。
- 与 1.0 同步提供网页版，作为简洁、可直接使用日历的官网。
- 2026-11-13 确认首个 1.0 的交付范围为 Mac＋网页版，iOS 在后续版本交付。发布前完成[1.0 验收清单](1.0验收清单.md)中适用的实机验证与发布决策。

## 1.0 前完成

- 核对项目、核心包与应用版本，补全中文变更记录。
- 完成适用于本次发布范围的核心、原生界面和网页验证。
- 完善网页版，复用 `packages/calendar-ui` 与 `packages/calendar-core`；首屏只承载日历及必要操作。
- 确定 GitHub 仓库归属、可见性和项目许可证，并配置正式部署目标及地址。
- 明确 Mac 分发签名、公证状态以及目标系统和架构，说明验证边界；如发布 iOS，完成 Xcode 工程、签名与设备验收。
- 核对调休快照与官方通知，保留数据来源及第三方许可证。
- 首个 Mac 1.0 内置正式更新源与公钥；配置独立保管的更新签名私钥，验收确认后下载、签名验证、安装重启与偏好恢复，详见[自动更新](自动更新.md)。

## 1.0 发布顺序

1. 完成代码、应用和网页版的验证，更新中文版本说明并提交。
2. 按用户已授权的安排创建或连接 GitHub 仓库，提交项目代码。
3. 建立正式 1.0 版本记录和应用下载产物，同步部署网页版官网。
4. 核验仓库版本、下载文件、官网日历、跨年与缺数据状态及手机首屏。
5. 向用户报告实际仓库链接、官网地址、版本和验证结果。

后续 Mac 版本通过 GitHub Actions 统一构建与发布，先发布签名更新包，最后发布稳定的 `latest.json` 清单；网页随站点部署更新。私钥、密码不入库，更新包签名不能替代 Apple 开发者签名与公证。

当前阶段不创建或推送 GitHub 仓库，不发布正式官网。2026-11-12 用户已单独授权部署[手机私有预览](手机预览.md)，用于 0.1.0 界面测试；不改变 1.0 正式发布门槛。上述正式发布步骤在条件满足后执行，不代表已有后台任务在监控版本。
