# 发布约定

## 当前授权与范围

- 2026-11-18 起，撤销应用自动发版授权。完成修改后先在本地执行适用验证，并向 IKUN 同学汇报改动和验证结果。应用发版由 IKUN 同学逐次决定，收到对当次发布的明确同意后才进入版本准备与发布流程。
- 等待决定期间可保留本地构建和已验证的提交。版本号、发布标签和正式发布流程留到当次发版获得同意后处理。官网部署与应用发版按实际交付范围分别处理。
- 仓库为 `cixiangtao/i-calendar`，公开可见，主许可证 MIT；项目信息、版本说明和提交描述使用中文。
- 首版交付 Mac arm64 与网页版，iOS 后续提供。Mac 采用 ad-hoc 本地签名，未通过 Apple 公证，须在 README、下载页与版本说明中明确披露。
- 未完成的驻留、真实登录、最低系统、手机真机和完整跨版本安装验收继续记录，不宣称已通过。

## 先判断交付范围

| 实际影响                                                                                  | 处理方式                       | 应用版本与产物                                    |
| ----------------------------------------------------------------------------------------- | ------------------------------ | ------------------------------------------------- |
| 官网样式、文案、布局、展示动效及 Web 专属行为                                             | 完成适用检查后独立部署 Pages   | 不递增版本，不创建标签、Release、Mac 包或更新清单 |
| Mac/iOS 功能、跨端共享界面与状态、核心规则、随应用分发的数据、原生行为、安装/更新或兼容性 | 本地验证后由用户决定是否发版   | 按实际范围递增版本，统一交付应用产物，可同步官网  |
| 纯文档、协作约定、验收记录、不改变应用交付内容的工具和 CI 维护                            | 验证后提交并推送               | 不自动发版或部署官网                              |
| 同轮同时包含官网与应用改动                                                                | 按应用范围本地验证，由用户决定 | 获同意后合并为一个应用版本                        |

判断依据是改动对已分发应用的实际影响，不是文件路径或 commit 类型。例：在 `packages/calendar-ui` 内只调整 Web 分支或 `web:` 样式，属于官网改动；调整 Mac 与 Web 共用的日期交互或历法计算，则属于应用改动。源码会进入同一前端构建，不等于所有改动都需要重新分发应用。

官网改动执行适用的 lint、格式、类型、测试与网页构建，并验证桌面/手机、浅深色及相关交互；不会因为仅部署官网就要求本机解锁或执行 Mac 打包。涉及原生或跨端行为时，仍按应用范围运行原生检查。纯文档检查内容、相关链接及格式即可。发布后的验收补记属于同次交付，不触发下一版。

## 官网独立部署

官网以 Git 提交 SHA 标识部署，不维护另一套应用版本号，不调用 `release:dry` / `release`，不生成应用标签、Release、安装包、签名或更新清单。部署后核对公开日历、引用资源和下载链接；失败时修复或恢复官网部署，不用递增应用版本来重试。

官网下载入口与展示的应用版本应读取最近已公开的正式应用版本及对应资源。仓库处于开发版本或预览状态时，不得直接把根清单中的未发布版本拼成公开下载地址；官网独立更新也不能覆盖应用更新源或修改既有 Release 附件。

**当前接入状态：** 目前官网部署由 `.github/workflows/release.yml` 中的 Pages 任务执行，仍依附应用标签发布，官网独立部署流水线尚未接入。本次仅更新约定，不宣称已有独立部署能力。后续仅官网改动需要上线时，应先接入独立的 Pages 构建与部署入口，并落实最近正式版下载信息的读取；不得通过提高应用版本绕过这一缺口。

## 应用版本号

以最近已公开的正式应用版本为基线。i日历的兼容承诺包括文档中公开的共享包 API、已记录的主题包等交换格式、既有用户数据的读取与迁移、明确承诺的安装和更新兼容范围。结合整版实际交付内容判断版本级别，多个变更按其中最高级别处理。规则依据见 [SemVer 2.0.0](https://semver.org/spec/v2.0.0.html)。

| 级别    | 应用提交信号                            | 适用改动                               | 从 `1.3.8` 递增示例 |
| ------- | --------------------------------------- | -------------------------------------- | ------------------- |
| `patch` | `fix`                                   | 向后兼容的修复                         | `1.3.9`             |
| `minor` | `feat`                                  | 新增兼容功能，或弃用仍可使用的公开能力 | `1.4.0`             |
| `major` | 标题带 `!` 或提交中有 `BREAKING CHANGE` | 引入与既有公开契约不兼容的变化         | `2.0.0`             |

发布预演查询 GitHub 最新公开正式版，从同名标签到 `HEAD` 扫描提交。同一批只按最高级别递增一次。范围 `web` 专用于仅影响官网的变更，`release`、`dev`、`ci` 专用于内部流程和工具维护，这些范围不参与应用升版。涉及安装、更新或其他已交付功能的改动使用对应的应用范围，例如 `fix(update)`。其余没有不兼容标记的提交类型不触发递增。

正式分发使用无前导零的 `MAJOR.MINOR.PATCH`，标签使用 `vMAJOR.MINOR.PATCH`。递增次版本时修订号归零，递增主版本时次版本和修订号归零。预发布标识和构建元数据是 SemVer 的扩展，正式发布入口只接收核心版本号。

本地验证后汇报预演建议及触发提交，供 IKUN 同学核对实际兼容性并决定当次是否发布。发布脚本校验版本格式、递增顺序和归零规则。

## 应用正式发布入口

`.github/workflows/release.yml` 是应用正式发布的唯一执行方。其普通分支推送不创建应用正式版；明确推送 `v<版本>` 标签触发，`workflow_dispatch` 仅用于恢复同一个正式标签的发布。

1. 标签、根版本、共享包、Tauri、Cargo 和仓库身份必须一致，标签提交必须属于 `main` 历史。
2. 在 Mac arm64 Runner 使用锁定 Node / pnpm / Rust，依次执行 `check:source`、Mac 签名更新包构建和 `check:mac`。Mac 打包时由 Tauri 构建核心 ESM 和官网，`check:mac` 运行 Rust 测试并冒烟检查打包后的应用。
3. 生成经过官方验签的更新清单和 SHA-256，保存实际受检产物；不在发布阶段重新构建另一份包。
4. 发布任务通过创建接口返回的身份定位新草稿 Release，先上传安装与更新包、签名及校验文件，最后上传 `latest.json`，产物齐全后公开为正式最新版。
5. 官网任务部署同次构建的 GitHub Pages 产物，地址为 `https://cixiangtao.github.io/i-calendar/`。
6. 从公开地址独立下载核对版本、签名、SHA-256、应用运行、更新清单与官网日历。

新仓库采用标签驱动流程，不要求预先建立 Release PR 控制器。本地只准备、验证、提交并推送明确的版本标签，不执行 `gh release create` 或本地部署。

## 使用 release-it 准备版本

本地统一通过锁定的 release-it 21.1.2 编排，配置位于 `release/release-it.json`。根 `package.json` 是版本来源，由公开 Plugin 接口读取；不调用 npm，不发布到 npm，也不在本地创建 GitHub Release。

1. 完成本地验证后，在跟踪 `origin/main` 的干净 `main` 运行 `pnpm run release:dry`。预演会显示建议版本和触发提交。没有涉及应用升版的提交时停止并提示，本地版本与 GitHub 最新正式版不一致时先核实发布现场。
2. 汇报预演结果。收到 IKUN 同学对当次发版的明确同意后，提交 `docs/releases/<版本>.md` 中文说明，首行使用 `# i日历 <版本>`。用预演中的版本执行正式命令。以下以预演建议 `2.1.0` 为例。

   ```sh
   pnpm run release 2.1.0
   ```

3. 实际执行先核对仓库身份、所有现有版本位置、Mac 构建环境与桌面状态，再重新推导建议版本。显式指定的级别或版本须与推导结果一致，同时核对远端分支包含关系、版本递增与已提交的说明。锁屏或桌面不可用仅提示窗口待验，继续其他门禁，不反复请求解锁，不修改系统锁屏设置。根版本、共享包、Tauri、Cargo 与当前版本文档同步。Cargo.lock 由 `cargo update --offline --workspace` 维护，其他文件按 oxfmt 格式化，历史版本说明保留原文。
4. 同步后依次执行 `check:source`、`build:mac` 和 `check:mac --defer-unavailable`，故本地正式准备仍需要 Mac 构建环境。源码检查覆盖 lint、格式、类型和 JavaScript / TypeScript 测试。可执行的质量门禁通过后（窗口待验单独记录，不声称通过），只允许版本元数据进入自动提交，创建 `chore(release): 🔨 发布 <版本> 正式版` 与附注标签 `v<版本>`。
5. release-it 的 `after:release` hook 使用 `git push --atomic` 一次推送 `main` 和这一个标签，不使用 `--follow-tags` 捎带其他本地标签。GitHub Actions 随标签启动正式构建、签名与发布，本地命令结束只表示已提交推送，不代表线上交付已完成。
6. 持续检查 Actions 三个任务及公开 Release、更新源和官网，按下述约定完成独立产物验证。

`release:dry` 实际读取 GitHub 正式版本与本地提交。写入和自定义 hook 只显示命令，实际测试和自定义门禁由正式命令执行。需要提前单独只读核对时可执行 `node scripts/release-version.mjs guard` 和 `node scripts/release-version.mjs validate <目标版本>`。

内置 `git.requireCleanWorkingDir` 与 `git.push` 关闭是有意的适配：自定义门禁仍严格检查已跟踪及未跟踪文件，而推送由原子 hook 完成，以避免默认回滚执行 `reset --hard` 或删除远端标签。检查失败保留版本差异供核实，不自动提交或推送；推送失败保留本地发布提交与标签。不要盲目重跑递增命令：先检查本地/远端的 `main` 和目标标签是否已更新，确认身份后补推同一提交与同一标签，或通过 Actions 恢复原发布。未完成发布时默认停止递增。

已经推送的候选标签若无法完成发布，先确认云端运行已结束、该标签没有公开 Release，并获得 IKUN 同学对替代版本的明确同意。保留原标签，在预演和正式命令前同时指定 `I_CALENDAR_REPLACE_UNPUBLISHED_TAG=v<失败候选版本>`。预演仍从最近公开版统计提交，若推导出的版本已被该候选占用，则按同一级别递增到下一版。

## 本机锁屏与窗口补验

锁屏不停止代码、类型、Rust 测试、构建、签名、云端发布、下载摘要及官网检查。release-it 的本地桌面准备与窗口检查显式启用 `--defer-unavailable`；只影响桌面不可用时的处理，非 Mac 环境仍无法准备 Mac 正式版。普通 `pnpm run check:mac` 保持严格检查，CI 不接受延后开关，正式流水线必须实际完成既有窗口与生命周期验证后才能发布。

本地延后模式在应用启动前和两种启动模式之间核对桌面；若运行失败后检测到锁屏，保留原始错误和输出并标为待验，不能宣称是锁屏引起，也不能当作通过。桌面可用时的失败仍返回非零状态。待验报告保存在不提交的 `work/native-checks/`，包含应用绝对路径、二进制 SHA-256、已有结果与原因。

桌面可用后运行：

```sh
pnpm run check:mac --resume
```

补验重新执行原应用的普通 / 后台完整检查，核对二进制摘要，产物被覆盖则拒绝沿用旧记录；已经通过的记录不会重复执行。若仍锁屏，保留待验并正常返回，不反复要求用户解锁。没有后台常驻补验进程，需要在后续桌面可用时执行该命令。

公开下载包可复用同一入口：

```sh
pnpm run check:mac --app-path "outputs/published-1.3.1/i日历.app" --defer-unavailable
```

`--app-path` 只选择受检包，不改用户安装位置或偏好。未指定时检查 `outputs/mac/i日历.app`。真实失败、摘要变化和其他工具错误不会因允许延后而被忽略。发布后的本机补验只补记同次交付结果，不递归发版。

## 配置与权限

- 根 `package.json` 为版本来源，各端配置同步；版本说明位于 `docs/releases/<版本>.md`。
- `release/config.json` 只含仓库、官网地址、更新地址与公钥；私钥不进入源码、网页或日志。
- 私钥与密码保存在维护者仓库外的受保护目录，并配置为当前仓库的 `TAURI_SIGNING_PRIVATE_KEY`、`TAURI_SIGNING_PRIVATE_KEY_PASSWORD` Secret；请独立备份，丢失后旧版不能直接信任新钥签名。
- 构建任务只读源码，Release 任务仅增加 `contents: write`，官网任务使用 `pages: write` 和 `id-token: write`。不执行来自外部 PR 的高权限发布。
- 更新签名使用官方 Tauri / Minisign，与 Apple Developer ID 和公证不同；首版不伪装成 Apple 已验证的软件。

## 失败恢复

公开附件统一使用 `i-calendar-<版本>-mac-arm64.*` 的 ASCII 文件名，避免 GitHub 对中文附件名进行规范化；安装包内的应用仍叫“i日历”。签名载荷只更改外部文件名，字节与原构建产物保持一致。

已存在的同名产物只在 SHA-256 一致时复用，不覆盖不同内容；旧版本不能覆盖最新版本。部分失败优先复用原构建产物，不因失败改用本地上传。首次公开前，允许将自己上传的草稿附件规范为 ASCII 名称，并纠正 `latest.json` 的下载地址和 `SHA256SUMS.txt`；变更前必须确认旧摘要与原构建元数据相同，不替换签名载荷。

若仅发布工具或流水线需要修正，在 `main` 提交修复后，通过同一个工作流的 `workflow_dispatch` 指定原版本 `tag` 和 `artifact_run`。恢复步骤校验原运行的标签提交、工作流路径、构建成功状态、产物有效期与 SHA-256，复用原签名应用；发布工具来自此次工作流的固定提交，不移动标签或重编译另一份 Mac 包。官网下载入口可从同版本的工作流源码重建，须检查核心、平台配置与依赖无变更，页面只允许修正下载链接。恢复时从完整列表查找已有草稿；新草稿直接使用创建响应中的编号和附件信息，不再依赖创建后的即时列表查询。不能将“按标签查询已发布版本”的 404 误当成草稿不存在。

标签与应用版本产物视为不可变。正式版本发布后发现影响已分发应用的代码或打包问题，应提高版本重新发布；不移动已有版本标签或静默替换下载包。仅官网问题按独立部署规则修复，已发布的 1.1.0、1.1.1 等历史版本与产物保留。
