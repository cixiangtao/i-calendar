# Mac 自动更新

## 用户体验

1.0.0 起的正式安装包包含更新能力、正式公钥与 HTTPS 更新源，之后的版本可从应用内更新；0.1.0 预览需要先手动安装 1.0.0。

- 默认开启“自动检查新版本”，位于“设置 → 关于 → 应用更新”，可关闭并保存。
- 启动、窗口重新获得焦点及每小时定时器提供检查机会；同一进程内自动检查每 24 小时最多一次，失败也计入限频。重新启动应用会重新检查，手动检查不受限频影响。
- 发现新版只显示轻量提醒，可查看版本说明或选择“稍后”；同一进程内不会再次提醒被推迟的同一版本，关于页仍可安装。
- 点击“下载并安装”才下载；显示进度，下载和安装互斥。官方 updater 验签成功后，再次等待最新偏好保存，最后安装并重启。
- 网络、签名、存储或安装失败显示重试提示，不主动重启；检查失败不影响正常查日历。
- 未配置正式源、开发构建和 `--smoke-test` 都不会请求更新。网页不显示 Mac 应用更新，网页版本随站点部署更新；iOS 后续按其分发渠道处理。

安装更新与“数据”页的调休更新相互独立，历法核心不依赖更新服务。

## 架构与安全边界

- 共享 UI 通过注入的 `AppUpdater` 操作平台能力；检查、下载和安装状态由 `AppUpdateController` 管理。
- Mac 使用 `tauri-plugin-updater 2.14.1`，通过 Rust 命令调用；下载地址和已检查的 Update 对象保留在 Rust，界面不能指定任意安装文件。
- 更新源与包下载只允许 HTTPS，不接受 URL 用户名、密码；HTTP 重定向也会被客户端拒绝。
- 使用官方 Minisign 验签，启用 `requireSignedVersion`。签名必须同时覆盖包内容和清单声明的版本；默认只接受更高版本，不开启降级。
- 下载先验签，安装前再次验签；发布工具也调用官方 `Update::verify` 离线校验。不自行实现密码算法。
- 应用只携带公钥，不携带签名私钥或 GitHub token。更新服务会收到正常 HTTPS 请求所带的网络信息，不发送偏好、调休缓存或用户数据。
- 更新包签名和 Apple Developer ID 签名、公证是两套机制；前者不能代替后者。正式分发仍须确定 Apple 签名与公证方案，并在实际安装位置验证升级权限。

## 正式配置

正式仓库为 `cixiangtao/i-calendar`。公开配置位于 `release/config.json`，更新入口为 GitHub Release 的 `releases/latest/download/latest.json`；Actions 从配置加载公钥与地址，并从仓库 Secret 加载以下私密配置：

| 变量                                 | 内容                                           | 是否秘密 |
| ------------------------------------ | ---------------------------------------------- | -------- |
| `I_CALENDAR_UPDATE_ENDPOINT`         | 稳定的 HTTPS `latest.json` 地址                | 否       |
| `I_CALENDAR_UPDATE_PUBKEY`           | Tauri 生成的 `.pub` 文件完整内容，不是文件路径 | 否       |
| `TAURI_SIGNING_PRIVATE_KEY`          | Tauri 签名私钥内容或私钥文件绝对路径           | 是       |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | 私钥密码；正式私钥使用独立保管的密码           | 是       |

公钥与地址在编译期写入 Mac；变更会触发重新编译。打包脚本会生成仅含公钥的临时配置，并开启更新产物生成。普通 `build:mac` 在已配置更新源时会拒绝运行，避免误发缺少签名更新产物的发布包。

首次正式密钥需由维护者生成并备份，私钥不能提交 Git、上传官网或写入明文 CI 配置。官方命令如下，使用绝对路径存到受保护位置；不要把真实密码直接写在 shell 命令中：

```sh
pnpm run tauri signer generate --write-keys /受保护目录/i-calendar.key
```

私钥丢失后，原安装包不能信任新公钥签出的更新；需要另行设计密钥迁移或手动安装，不能临时换钥继续发布。

## 打包与清单

配置好上述环境变量后：

```sh
pnpm run check
pnpm run check:native
pnpm run build:mac:update
pnpm run check:mac
```

脚本使用当前宿主架构打包，不把 arm64 构建声明为 Intel 构建。产物包括普通 ZIP、`.app.tar.gz` 更新包和 `.app.tar.gz.sig` 签名；输出到 `outputs/`。它会离线校验更新包与当前根版本相符，任何失败都会让命令失败。

将本次中文 Release Notes 保存到文件后生成清单。以下下载地址仅为占位示例，正式发布必须替换：

```sh
pnpm run release:manifest \
  --arm64 outputs/i日历-1.0.0-mac-arm64.app.tar.gz \
  --arm64-url https://发布域名/版本/i日历-1.0.0-mac-arm64.app.tar.gz \
  --notes work/本次版本说明.md
```

版本读取根 `package.json`，不由命令随意覆盖。脚本读取相邻 `.sig`，逐架构验证文件签名、版本及清单目标，成功后原子写入 `outputs/latest.json`。如提供已实际构建和验证的 Intel 包，可同时传 `--x64` 与 `--x64-url`；没有该架构的包就不写对应平台。

首次 1.0 发布后，以 GitHub Actions 作为正式发布的唯一执行方：使用受保护的签名秘密，在每次新版本发布时构建、验签、发布不可变的版本产物，最后更新稳定清单。仓库未确定前不创建含虚构地址的自动发布工作流，也不上传任何产物。

顺序必须是“更新包与签名先可下载 → 清单最后可下载”。同一版本不要覆盖包内容；修复发布错误应提高版本重新构建。正式发布前验证 HTTPS 清单、全部声明架构的下载地址和旧版真实升级，不能只用本地打包结果替代线上验证。

## 验证与待验收

- 共享状态测试覆盖自动限频、手动重试、稍后提醒、操作互斥、偏好迁移和安装前保存失败阻断。
- Rust 测试覆盖配置与并发；官方公开签名向量覆盖正确内容通过、内容篡改拒绝、伪造版本拒绝、架构缺失拒绝。离线验证工具使用 MockRuntime，不触发联网、安装或窗口操作，也不进入生产应用。
- UI 模拟覆盖新版入口、更新说明、下载状态、安装状态、失败后可重试、手动检查最新版本及未配置状态；模拟不会实际安装或重启应用。
- 1.0.0 已配置正式地址与更新公钥，长期私钥由仓库外目录与 GitHub Secret 保管。首版仍为 Apple ad-hoc 签名、未公证；正式安装位置的跨版本安装重启与偏好恢复仍需后续实机验收，不将签名工具验证替代为完整升级实测。
